================================================================================
1. PROJECT OVERVIEW
================================================================================

RaspyJack is a portable Raspberry Pi offensive security toolkit with:
- A physical LCD menu driven by GPIO buttons.
- A WebUI dashboard and live screen mirror.
- A browser Payload IDE for viewing, editing, and launching payloads.
- A filesystem-based payload launcher.
- Loot collection under loot/.
- Integrations with Linux networking tools, WiFi adapters, Bluetooth, GPS, NFC,
  SDR hardware, USB gadget mode, JanOS ESP32-C5 firmware, and external services.

Core files:
- raspyjack.py: main device UI, menu, payload discovery, payload execution.
- web_server.py: HTTP server, payload list/start/status APIs, Payload IDE routes.
- device_server.py: WebSocket screen mirror and input forwarding.
- rj_input.py: virtual button bridge used by WebUI and payloads.
- LCD_1in44.py / LCD_Config.py: LCD driver and SPI/GPIO configuration.
- payloads/: standalone Python payloads grouped by category.
- payloads/_input_helper.py: unified GPIO + WebUI input helper.
- payloads/_display_helper.py: scaled drawing helper for 128/240/Cardputer layouts.
- payloads/_keyboard_helper.py: LCD text entry helper.
- payloads/_iface_helper.py: network interface detection and LCD interface picker.
- payloads/_gps_helper.py: GPS autodetection and gpsd startup.
- payloads/_janos_helper.py: UART transport for JanOS ESP32-C5 firmware.
- payloads/sdr/_sdr_core.py: RTL-SDR / SoapySDR abstraction.
- EXTENSIONS/: optional trigger/action helper API.
- DNSSpoof/: phishing/captive portal site templates.
- Responder/: vendored Responder stack.
- vendor/ragnar/: vendored Ragnar stack controlled by the Ragnar payload.

================================================================================
2. PAYLOAD RUNTIME MODEL
================================================================================

Payload discovery:
- raspyjack.py walks payloads/ recursively.
- Only .py files are included.
- Files whose names start with "_" are helper modules and are not launchable.
- Hidden directories and __pycache__ are skipped.
- The first path segment is the category.
- Root-level payloads, if any, are treated as "general".
- Subdirectories become nested folders in the LCD payload menu.

Launch paths:
- LCD: Main Menu -> Payload -> category -> payload.
- WebUI: payload list/start APIs write a request file read by raspyjack.py.
- Payload IDE: browser editor can save and run payload files.
- Favorites: loot/Favorites/favorites.json injects selected payloads into the main menu.
- Autostart: loot/Autostart/autostart.json launches one payload on boot.
- Utility launchers: payload_scheduler, button_combo, and some manager payloads can
  launch or coordinate other payloads.

Execution lifecycle:
1. raspyjack.py resolves the selected file under payloads/.
2. It writes /dev/shm/rj_payload_state.json with running=true and the payload path.
3. It sets screen_lock so the main UI stops drawing.
4. It clears the LCD.
5. It runs python3 <payload> as a blocking subprocess.
6. stdout and stderr are appended to loot/payload.log.
7. On exit, raspyjack.py rewrites payload state to idle.
8. GPIO and LCD are reinitialized.
9. The main menu is redrawn.

Important runtime constraints:
- Only one foreground payload owns the LCD and buttons at a time.
- The parent menu is blocked while a payload runs.
- WebUI Stop is cooperative: it sends the KEY3 virtual button. Payloads must poll
  get_button() and exit on KEY3.
- Payloads should use KEY3 as the universal exit/back action.
- Payloads should clean up LCD, GPIO, network modes, subprocesses, and temporary
  services before returning to the menu.

Display and input:
- The LCD driver mirrors frames to /dev/shm/raspyjack_last.jpg for WebUI streaming.
- Payloads that call LCD.LCD_ShowImage() automatically appear in the WebUI mirror.
- _input_helper.get_button() checks WebUI virtual buttons first, then GPIO.
- _input_helper respects the display flip setting from gui_conf.json.
- _keyboard_helper.lcd_keyboard() supports text entry on the LCD and remote text
  sessions where supported.

Standard controls:
- UP/DOWN/LEFT/RIGHT: navigate, scroll, move cursor, or adjust values.
- OK: confirm, select, start, pause, or activate focused item.
- KEY1: mode switch or primary secondary action.
- KEY2: stop sub-action, reset, backspace, or alternate action.
- KEY3: mandatory exit to the RaspyJack menu.

Common output locations:
- loot/payload.log: captured stdout/stderr from payload subprocesses.
- loot/Handshakes/: WPA handshakes and related WiFi captures.
- loot/NFC/: saved NFC dumps and card data.
- loot/SDR/: SDR and Sub-GHz captures.
- loot/GoodPortal/, loot/Favorites/, loot/Autostart/: payload-specific state.
- config/: payload configuration files and profiles.

================================================================================
3. HARDWARE AND LINUX INTEGRATION
================================================================================

Baseline device:
- Raspberry Pi running Linux.
- Waveshare-style LCD HAT or compatible display.
- GPIO buttons using BCM pins:
  UP=6, DOWN=19, LEFT=5, RIGHT=26, OK=13, KEY1=21, KEY2=20, KEY3=16.

Display support:
- ST7735 128x128.
- ST7789 240x240.
- Cardputer-style 320x170 profile.
- Payload UI should be designed in 128-base coordinates and scaled using
  _display_helper.ScaledDraw and scaled_font.

Privilege assumptions:
- RaspyJack services and payloads are expected to run as root.
- Many payloads need CAP_NET_RAW, CAP_NET_ADMIN, monitor mode, iptables, raw
  sockets, Bluetooth HCI access, USB gadget configuration, or systemd control.

Dual WiFi policy:
- Onboard Pi WiFi is reserved for normal connectivity and WebUI access.
- External USB WiFi adapters are used for monitor mode, packet injection, AP mode,
  deauth, capture, captive portal, and evil twin workflows.
- _iface_helper sorts USB WiFi before onboard WiFi and can require monitor support.
- Preferred adapter families include RTL8812AU/RTL88XXAU, AR9271/ath9k_htc,
  MT7921U, RTL8188EUS, and related monitor-capable chipsets.

Monitor mode pattern:
- rfkill unblock wifi.
- Unmanage the attack interface with NetworkManager when possible.
- Stop per-interface wpa_supplicant interference.
- Switch interface type with iw, or fall back to airmon-ng.
- Verify whether the active interface is iface or ifacemon.
- Restore managed mode and NetworkManager after the attack.

AP/captive portal pattern:
- Use hostapd for AP mode.
- Use dnsmasq for DHCP/DNS.
- Use iptables/nft/sysctl for routing or captive behavior when needed.
- Kill or clean stale hostapd/dnsmasq instances on exit.

Bluetooth:
- Uses BlueZ, hci0 by default, bluetoothctl, hciconfig, hcitool, l2ping, bleak,
  and bluepy depending on payload.
- Some raw HCI payloads temporarily stop bluetoothd.

GPS:
- _gps_helper scans /dev/serial/by-id, ttyACM*, ttyUSB*, ttyS*, and ttyAMA*.
- It detects NMEA output, releases serial-getty on UART GPS, and starts gpsd -n.
- Wardriving and hardware GPS payloads consume gpsd output.

JanOS ESP32-C5:
- wifi/janos_c5.py controls ESP32-C5 JanOS firmware over UART.
- JanOS performs WiFi/BLE RF work; RaspyJack is the LCD controller and command UI.
- Commands include ping, scan_networks, select_networks, start_deauth, stop,
  start_blackout, start_sniffer, show_sniffer_results, scan_bt.

NFC/RFID:
- NFC payloads use PN532 or compatible readers via helper modules.
- Workflows include scanning, dumping, cracking, writing, formatting, and browsing
  saved card data.

SDR/Sub-GHz:
- SDR payloads use RTL-SDR, rtl_sdr, rtl_433, rtl_fm, dump1090, multimon-ng, and
  optional SoapySDR/HackRF style backends.
- _sdr_core kills stale rtl_* processes before starting a new SDR session.

USB:
- USB payloads use USB host monitoring, USB gadget mode, HID gadget, mass storage
  gadget, USB Ethernet, and evdev where available.

================================================================================
4. USING PAYLOADS
================================================================================

On device:
1. Boot RaspyJack and wait for the main LCD menu.
2. Select Payload.
3. Choose a category.
4. Select the payload.
5. Follow the on-screen controls.
6. Press KEY3 to exit.
7. Review loot files or loot/payload.log if the payload reports an error.

From WebUI:
1. Open the RaspyJack WebUI from the device IP.
2. Use the Payload panel or Payload IDE.
3. Start a payload by path.
4. Watch the live LCD mirror.
5. Use virtual controls; Stop sends KEY3.

When to prefer WebUI:
- Longer text entry.
- Monitoring a payload while the device is not physically accessible.
- Editing or testing payloads through the Payload IDE.

When to prefer the device LCD:
- Field operation.
- Quick confirmation/control loops.
- Payloads that require physical proximity to WiFi/BLE/NFC/Sub-GHz targets.

7. CREATING PAYLOADS - SHORT REFERENCE
================================================================================

Use payloads/examples/_payload_template.py as the starting point. For the full
project skill, see .cursor/skills/raspyjack-payload-authoring/SKILL.md.

Required behavior:
- Place the file under payloads/<category>/<name>.py.
- Do not start the filename with "_" unless it is a helper.
- Use _input_helper.get_button() for every interactive loop.
- Use KEY3 as exit.
- Use _display_helper.ScaledDraw and scaled_font for screen drawing.
- Use _keyboard_helper.lcd_keyboard for text entry.
- Use _iface_helper.select_interface for WiFi/Ethernet selection.
- Keep the UI loop responsive; long work belongs in a worker thread or subprocess
  with cooperative cancellation.
- Write durable results under loot/<PayloadName>/ or an existing category loot
  directory.
- Let stdout/stderr go to loot/payload.log for diagnostics.
- Clean up monitor mode, AP mode, gpsd/hostapd/dnsmasq/tcpdump/rtl_* processes,
  GPIO, and LCD state before exit.

Optional integration:
- Add an icon to menu_icons.json under the payloads section, keyed by the display
  label with a leading space, for example " deauth".
- Use EXTENSIONS.api only when a payload needs reusable trigger/action gates.
- Use Favorites Manager for operator shortcuts instead of hardcoding top-level
  menu entries.

################################################################################
##  1.  PRZEGLĄD PROJEKTU (PROJECT OVERVIEW)
################################################################################

Raspyjack to framework do pentestingu oparty na Raspberry Pi z wyświetlaczem
LCD 1.44" (128x128, ST7735S, SPI). Łączy fizyczne przyciski GPIO, interfejs
webowy (WebUI) i system payloadów w jedną platformę do skanowania sieci,
ataków MITM, przechwytywania WiFi, rozpoznania BLE i zdalnego dostępu.

Architektura:
  raspyjack.py        — główny daemon (GUI + menu + ataki)
  web_server.py       — HTTP REST API (port 8080)
  device_server.py    — WebSocket (port 8765, frame mirror + shell + input)
  payloads/           — niezależne skrypty Python uruchamiane w subprocesie
  wifi/               — moduły zarządzania WiFi (manager, switch, route)
  web/                — frontend (dashboard + IDE edytora payloadów)
  Responder/          — LLMNR/NBNS/mDNS poisoner
  DNSSpoof/           — phishing sites + ettercap
  Navarro/            — OSINT username checker

Sekwencja startu:
  1. Sprawdzenie root (wymaga sudo)
  2. GPIO BCM init + LCD init
  3. Wczytanie gui_conf.json (piny, kolory, ścieżki)
  4. Uruchomienie wątków: _stats_loop (temp/status co 2s), _display_loop (LCD co 100ms)
  5. System menu (DisposableMenu) — główna pętla nawigacji

Wątki tła:
  _stats_loop()    — odczyt temperatury CPU + status (scan/MITM/Responder) co 2s
  _display_loop()  — odświeżanie LCD co 100ms + zapis JPEG do /dev/shm/ dla WebUI

Kluczowe zmienne globalne:
  _stop_evt           — threading.Event do zamykania wątków
  screen_lock         — blokada UI podczas wykonywania payloadu
  _status_text        — aktualny tekst statusu na toolbarze LCD
  _temp_c             — temperatura CPU
  draw_lock           — thread-safe rysowanie na LCD
  FRAME_MIRROR_ENABLED — mirror ekranu do WebUI (domyślnie włączony)

##  2.  HARDWARE & GPIO
################################################################################

Wyświetlacz: LCD 1.44" 128x128 pikseli, sterownik ST7735S, połączenie SPI.
Pliki: LCD_1in44.py (driver), LCD_Config.py (konfiguracja SPI/GPIO dla LCD).

Przyciski fizyczne (domyślne piny BCM):
  KEY_UP_PIN    = GPIO 6     — nawigacja w górę
  KEY_DOWN_PIN  = GPIO 19    — nawigacja w dół
  KEY_LEFT_PIN  = GPIO 5     — cofnij / wstecz
  KEY_RIGHT_PIN = GPIO 26    — potwierdź / dalej
  KEY_PRESS_PIN = GPIO 13    — potwierdź (center joysticka)
  KEY1_PIN      = GPIO 21    — przełączanie trybu widoku / funkcja kontekstowa
  KEY2_PIN      = GPIO 20    — funkcja kontekstowa
  KEY3_PIN      = GPIO 16    — wstecz / wyjście

Debouncing: 0.10s | Repeat delay: 0.25s | Repeat interval: 0.08s

Plik konfiguracji: gui_conf.json
  Sekcje: PINS (mapowanie GPIO), COLORS (7 kolorów hex), PATHS (ścieżka startowa obrazów)

  - load_config() / save_config() — trwałe przechowywanie w JSON
  - get_pin(name) / set_pin(name, number) — zarządzanie pinami
  - Globalny singleton: gpio_config = GPIOConfig()

##  3.  INPUT — SYSTEM WEJŚCIA
################################################################################

--- input_events.py (zaawansowany menedżer zdarzeń) ---
Klasa ButtonEventManager — generuje zdarzenia na podstawie pollingu GPIO:
  PRESS        — przycisk naciśnięty
  RELEASE      — przycisk zwolniony
  CLICK        — krótkie naciśnięcie
  DOUBLE_CLICK — dwa naciśnięcia w oknie 0.30s
  LONG_PRESS   — przytrzymanie 0.80s
  REPEAT       — cykliczne zdarzenia przy przytrzymaniu (start 0.50s, interwał 0.15s)

Format zdarzenia: {"type": "CLICK", "button": "KEY_UP_PIN", "ts": 12345.67}
Polling co 5ms. Opcjonalny plugin_dispatch(event) callback.

--- rj_input.py (most wirtualnych przycisków dla WebUI) ---
Unix socket: /dev/shm/rj_input.sock (AF_UNIX, datagram, chmod 0o666)
Protokół JSON: {"type":"input", "button":"UP|DOWN|LEFT|RIGHT|OK|KEY1|KEY2|KEY3", "state":"press|release"}
Mapowanie: UP→KEY_UP_PIN, DOWN→KEY_DOWN_PIN, LEFT→KEY_LEFT_PIN,
           RIGHT→KEY_RIGHT_PIN, OK→KEY_PRESS_PIN, KEY1→KEY1_PIN itd.
Umożliwia sterowanie urządzeniem z przeglądarki webowej.

Standardowy wzorzec payloadu:
  1. sys.path.append + importy (RPi.GPIO, LCD_1in44, PIL, _input_helper)

  4. Main loop: get_button() → przetwarzanie → aktualizacja LCD → sleep

=== install_raspyjack.sh (~800+ linii) ===

Cel: Kompletna instalacja Raspyjack na czystym Raspberry Pi OS.

Krok 1 — Detekcja konfiguracji:
  /boot/firmware/config.txt (Bookworm) lub /boot/config.txt (starsze)

Krok 2 — Pakiety APT (80+):
  Python3 + NumPy, Pillow, Scapy, cryptography
  Sieć: nmap, tcpdump, arp-scan, dsniff, ettercap-text-only, aircrack-ng
  BLE: bluepy (kompilacja ze źródeł via setup.py)
  I2C/SPI: i2c-tools, python3-spidev
  Fonty: DejaVu + FontAwesome 6.5.1 (wget)

Krok 3 — Konfiguracja kernela (dtparam):
  i2c_arm=on, i2c1=on, spi=on
  dtoverlay=spi0-2cs
  Moduły: i2c-bcm2835, i2c-dev, spi_bcm2835, spidev

Krok 4 — WiFi Interface Pinning (KRYTYCZNE):
  Wykrywanie onboard (SDIO/MMC) vs USB dongles.
  /etc/systemd/network/10-onboard-wifi.link (systemd priority)
  /etc/udev/rules.d/70-raspyjack-wifi.rules (fallback)
  Wymuszenie: onboard → wlan0, pierwszy USB → wlan1.
  Zapobiega losowemu zmienianiu nazw przy rebootach.

Krok 5 — Usługi SystemD:
  raspyjack.service         — główny daemon
  raspyjack-device.service  — WebSocket server
  raspyjack-webui.service   — HTTP server
  raspyjack-pin-wifi.service — boot-time WiFi pinning

Krok 6 — Sekrety:
  .webui_token          — 32 znaki URL-safe (auth token)
  .webui_session_secret — 48 znaków URL-safe (HMAC secret)
  Uprawnienia: 0600

  HTTPS reverse proxy: localhost + multi-IP (eth0, wlan0, tailscale0)
  /ws* → 127.0.0.1:8765 (WebSocket)
